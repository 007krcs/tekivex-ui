# Accessibility audit — WAI-ARIA APG pattern review (2026-07-08)

An adversarially-verified audit of the interactive components against their WAI-ARIA
Authoring Practices (APG) pattern. 5 review agents proposed findings; each was then
independently verified against the current source (default verdict: refuted). Only
**confirmed** defects are listed. Result: **35 confirmed** (4 high, 26 medium, 5 low).

This is why the unqualified "WCAG 2.1 AAA" claim is being walked back to an honest
baseline until these are cleared. Fixed items are struck through as cycles land.

## HIGH

> **All 4 HIGH items fixed in v3.29.0** (Dropdown menu-button keyboard support,
> Menu `aria-activedescendant`, Cascader keyboard operability, Carousel WCAG
> 2.2.2 pause control), each with a regression test in
> `tests/a11y-high-fixes.test.tsx`. The 26 medium + 5 low remain, tracked below
> for subsequent cycles.


### 1. TkxDropdown trigger wrapper
- **Violation:** The dropdown trigger is a plain <div ref={triggerRef} onClick={toggleOpen}> carrying aria-haspopup="menu", aria-expanded, and aria-controls but with no role="button", no tabIndex, and no onKeyDown. The menu-button semantics sit on a wrapper that is neither focusable nor keyboard-operable. With a non-interactive trigger (e.g. <span>Menu</span>) a keyboard-only user cannot tab to or activate it, so the menu can only be opened with a mouse — WCAG 2.1.1 (Keyboard, Level A).
- **Fix:** Make the wrapper a real, keyboard-operable control (or forward the semantics onto the trigger). Minimal fix on the wrapper div: add role="button", tabIndex={disabled ? -1 : 0}, and an onKeyDown that opens on Enter/Space/ArrowDown and closes on Escape, e.g.: onKeyDown={(e) => { if (disabled) return; if (e.key === 'Enter' || e.key === ' ' || e.key === 'ArrowDown') { e.preventDefault(); setOpen(true); } else if (e.key === 'Escape' && isOpen) { setOpen(false); } }} role="button" tabIndex={disabled ? -1 : 0} Then add a regression test: render with trigger={<span>Menu</span>}, tab to the trigger (or fireEvent.keyDown with key 'Enter'/'ArrowDown'), and assert role="menu" appears. Longer term, prefer cloning the trigger element to attach the ARIA/keyboard props to the actual interactive node so aria-haspopup/aria-expanded/aria-controls land on the focused control rather than a wrapper.

### 2. TkxMenu
- **Violation:** Menu keyboard navigation moves only a visual highlight (activeIdx → backgroundColor). DOM focus stays on the role="menu" container (panelRef.focus(), tabIndex=-1); item rows have tabIndex=-1 and no id; and the container has no aria-activedescendant. Neither roving tabindex nor aria-activedescendant is implemented, so no focus (real or virtual) ever lands on the active item.
- **Fix:** Adopt the aria-activedescendant model that fits the existing "container holds focus" design: (1) give each interactive row a stable id, e.g. id={`${panelId}-item-${myFlatIdx}`}, on all four row types; (2) on the role="menu" container add aria-activedescendant={activeIdx >= 0 ? `${panelId}-item-${activeIdx}` : undefined}. This makes the AT announce each traversed item's label/role/checked/expanded state as ArrowUp/ArrowDown change activeIdx, with no other logic changes. (Alternative: roving tabindex — set the active row tabIndex={0} and call its .focus() in the activeIdx effect, resetting others to -1 — but activedescendant is the smaller, lower-risk change here.) Add a test asserting the container's aria-activedescendant updates on ArrowDown/ArrowUp.

### 3. TkxCascader
- **Violation:** Once opened, the cascader tree is completely keyboard-inoperable. The treeitem <li> elements (lines 183-201) use onClick/onMouseEnter with no tabIndex, so they are not focusable. The role="tree" container (lines 151-166) has no aria-activedescendant. handleKeyDown (lines 132-145) handles only Escape and Enter/Space (Enter/Space merely opens the popup when closed) — there are no Arrow/Home/End/Left/Right handlers. The only focusable element is the trigger button (line 237); focus never enters the tree and there is no active-descendant model, so navigation and selection are mouse-only. WCAG 2.1.1 Keyboard (Level A) failure.
- **Fix:** Implement an active-descendant keyboard model on the open tree. Concretely: (1) Track a focused cell as {col, index} in state. (2) Give each treeitem li a stable id and set aria-activedescendant on the role="tree" container to the focused item's id; render a visible focus ring on that item. (3) Keep DOM focus on the trigger button (or move it to the tree container with tabIndex=0) and extend handleKeyDown, when open, to handle: ArrowDown/ArrowUp to move within the current column (skipping disabled items), ArrowRight/Enter on a parent to descend into its children column (updating hoverPath), ArrowLeft to move back to the parent column, Home/End to jump to first/last item, and Enter/Space on a leaf to call handleSelect and commit. (4) Reset the focused cell to the current value path when the popup opens. This restores the standard ARIA tree/combobox keyboard interaction and satisfies WCAG 2.1.1.

### 4. TkxCarousel
- **Violation:** WCAG 2.2.2 Pause, Stop, Hide (Level A): when autoPlay is enabled, slides advance on a setInterval (lines 236-240) with the only pause path being the viewport's onMouseEnter/setPaused(true) (line 377). There is no pause/play button and no focus-based pause, so keyboard-only and many AT users cannot stop the continuous, indefinite rotation.
- **Fix:** Add a keyboard-accessible pause/play toggle button inside the carousel controls that toggles the existing `paused` state, with an aria-label like "Pause automatic slide rotation" / "Resume automatic slide rotation" (only render it when autoPlay is true). Additionally, add onFocus/onBlur (or focusin/focusout) handlers on the container div at line 340 that call setPaused(true) on focus-in and setPaused(false) on focus-out, mirroring the existing hover behavior so moving keyboard focus into the carousel pauses rotation. Optionally, do not auto-start when useReducedMotion() is true. This satisfies SC 2.2.2 by giving keyboard and AT users a reachable mechanism to stop the motion.

## MEDIUM

### 1. TkxSelect trigger — multi-select tag remove
- **Violation:** WCAG 2.1.1 (Keyboard) + invalid HTML content model: interactive span role=&quot;button&quot; tabIndex=-1 controls (per-tag ✕ and Clear all) are rendered as descendants of the native &lt;button&gt; trigger. Nesting interactive content inside a button is invalid HTML, and tabIndex=-1 keeps both out of the tab order. handleTriggerKeyDown (lines 364-404) has no Backspace/Delete or clear key handling, so there is no keyboard path to Clear all at all; individual tags can only be removed by reopening the listbox and toggling each option off.
- **Fix:** The tag ✕ and Clear-all must not be interactive descendants of the &lt;button&gt;. Options: (1) Convert the trigger container from a native &lt;button&gt; to a &lt;div role=&quot;combobox&quot; tabIndex={0}&gt; (moving the open/keydown handlers onto it), and render each tag remove and the clear control as real &lt;button type=&quot;button&quot;&gt; siblings inside it so they enter the tab order and are individually operable via Enter/Space. Or (2) keep the button as the open affordance but lift the tags row and clear control into a sibling wrapper div positioned within the control (absolute/flex layout), rendered as real &lt;button&gt;s outside the trigger button. In either case give the remove buttons real aria-labels (already present) and add Backspace-on-trigger to remove the last tag as a keyboard convenience. Update TkxSelect.test to assert Tab reaches the clear control and each tag ✕ and that Enter/Space activates them.

### 2. TkxDropdown
- **Violation:** Single-select menu items set aria-selected={!multiSelect ? isSelected : undefined} on an element with role="menuitem". aria-selected is not a supported state for role="menuitem", so assistive technology ignores it and the selected state is conveyed only visually (the checkmark SVG at lines 656-661), never programmatically. Selectable menu items must be role="menuitemradio" (single-select) with aria-checked. The submenu children (lines 509-516) repeat the same aria-selected-on-menuitem mistake.
- **Fix:** Give selectable items the correct role and state. Replace role="menuitem" for selectable, non-submenu items with a role/state pair driven by mode: for single-select use role="menuitemradio" aria-checked={isSelected}; for multi-select use role="menuitemcheckbox" aria-checked={isSelected}; keep role="menuitem" only for action items and submenu parents (which should not carry aria-selected/aria-checked at all). Concretely at lines 450-453: role={hasSubmenu ? 'menuitem' : (multiSelect ? 'menuitemcheckbox' : 'menuitemradio')}, aria-checked={hasSubmenu ? undefined : isSelected}, and remove aria-selected entirely. Apply the same change to the submenu children at lines 514-516 (remove aria-selected, use menuitemradio/menuitemcheckbox + aria-checked). Then update tests/TkxDropdown.test.tsx (lines 200-214) to query aria-checked instead of aria-selected.

### 3. TkxSelect
- **Violation:** In searchable mode, aria-activedescendant/aria-controls/combobox role live on the trigger button, but DOM focus is moved to a separate plain search input that has none of them, so active-option changes are not exposed to the focused element.
- **Fix:** Make the focused element carry the combobox contract. On the search <input> (lines 539-559) add: role="combobox", aria-expanded={true}, aria-controls={listboxId}, aria-activedescendant={activeOptionId}, and aria-autocomplete="list". This matches the APG editable-combobox pattern where the text input is the combobox. Correspondingly, when searchable the trigger button should no longer be the combobox owner (drop or downgrade its role/aria-activedescendant/aria-controls to avoid two competing combobox nodes). Add a regression test that opens a searchable select, presses ArrowDown on the search input, and asserts input.getAttribute('aria-activedescendant') matches the newly-active option id (mirroring the existing non-searchable test at line 420).

### 4. TkxCommandPalette
- **Violation:** Modal dialog (role="dialog" aria-modal="true", lines 331-333) implements no focus trap and does not make background content inert/aria-hidden. The panel onKeyDown (lines 287-316) handles Arrow/Enter/Escape/Home/End but never Tab/Shift+Tab, and no useFocusTrap hook is used (unlike sibling TkxCommand.tsx, which traps Tab). The only focusable node in the dialog is the search input, so one Tab press moves focus to page controls behind the modal. Violates WAI-ARIA APG modal dialog pattern and WCAG 2.4.3 (Focus Order).
- **Fix:** Add a focus trap to the inner panel. Simplest path: reuse the existing useFocusTrap hook from TkxCommand.tsx (or promote it to src/hooks) and attach its ref to the panel <div> at line 350 so Tab/Shift+Tab cycle within the dialog. Alternatively, add a case 'Tab' to onKeyDown that collects focusable descendants and wraps focus at the ends (preventDefault when wrapping). Also (a) capture document.activeElement on open and restore it on close, and (b) mark background content inert (or aria-hidden) while open for AT parity. Add a regression test asserting Tab from the input keeps focus inside [data-testid="tkx-command-palette"].

### 5. TkxCommandPalette
- **Violation:** Dialog (Modal) does not restore focus on close. The open effect focuses the input but never records document.activeElement, and every close path (Escape, backdrop click, hotkey toggle, command run) calls setOpen(false), which unmounts the portal (if (!open) return null) without returning focus to the invoking element — focus falls to document.body.
- **Fix:** Capture the invoking element on open and restore it on close. Add a ref and extend the open effect: const restoreFocusRef = useRef<HTMLElement | null>(null); useEffect(() => { if (open) { restoreFocusRef.current = document.activeElement as HTMLElement | null; setQuery(''); setActiveIdx(0); requestAnimationFrame(() => inputRef.current?.focus()); } else { // restore focus to the element that had it before opening const el = restoreFocusRef.current; restoreFocusRef.current = null; if (el && typeof el.focus === 'function' && document.contains(el)) { el.focus(); } } }, [open]); Because this effect must run on the false transition too, ensure it is not gated by an early return before the hook. (The component already returns null after all hooks, so the effect still runs on close.) Guard with document.contains(el) to avoid focusing a detached node.

### 6. TkxCascader
- **Violation:** Combobox + Tree wiring is incomplete. The trigger button (role="combobox", line 240) has no aria-controls and no aria-activedescendant, and the popup div (role="tree", line 153) has no id, so the combobox↔popup relationship is not conveyed. The tree structure is also malformed: the per-column lists render as flat sibling role="group" elements directly under role="tree" (lines 167-170) instead of nesting each child group inside its parent treeitem (or using aria-owns), and the treeitem li elements (lines 183-188) omit aria-level, aria-setsize, and aria-posinset. Assistive tech therefore cannot convey the option hierarchy or the trigger-to-popup relationship.
- **Fix:** 1) Give the tree a stable id (e.g. useId) and set aria-controls={treeId} on the combobox button; keep aria-haspopup="tree". 2) Track the active option and set aria-activedescendant on the button to that treeitem's id (give each li a deterministic id), updating it as hoverPath changes. 3) Fix the tree hierarchy: either (a) nest each child column's role="group" inside the parent treeitem it descends from, or (b) keep the visual column layout but link them with aria-owns on the parent treeitem pointing to the child group's id. 4) Add aria-level (colIdx+1), aria-setsize (col.length), and aria-posinset (index+1) to each treeitem so AT can announce depth and position. Add tests asserting button has aria-controls matching the tree id, and that treeitems expose aria-level/setsize/posinset.

### 7. TkxAccordion — AnimatedPanel
- **Violation:** Collapsed accordion panel is only visually clipped (height:0 + overflow:hidden, set imperatively on outerRef) but is never removed from the accessibility tree or tab order — no hidden attribute, no aria-hidden, no inert, no display:none/visibility:hidden. Focusable content inside a collapsed panel (e.g. a link/button in item.content) remains Tab-reachable and screen-reader-readable while aria-expanded=false, violating the APG Accordion/Disclosure requirement (and WCAG 2.4.3 Focus Order / 1.3.1) that a collapsed panel be hidden.
- **Fix:** Hide the collapsed panel from AT and tab order without breaking the height animation by only hiding once it is fully closed. Add state, e.g. const [fullyClosed, setFullyClosed] = useState(!isOpen); in the close transitionEnd handler (line 249 branch) call setFullyClosed(true), and when opening set setFullyClosed(false) before/at the start of the open effect (around line 219). Then on the outer region div apply `hidden={fullyClosed}` (or, to preserve role/labelledby semantics during measurement, `inert={fullyClosed || undefined}` plus `aria-hidden={fullyClosed || undefined}`). For the reduced-motion path (lines 201-205) and the initial-render effect (lines 180-191) there is no transition event, so set fullyClosed directly to match isOpen there. This keeps the open/close animation intact while ensuring a collapsed panel's content is neither focusable nor exposed to screen readers.

### 8. TkxStepper
- **Violation:** Interactive list / button semantics: when `clickable` is true, each step's clickable node is a plain <div onClick> with cursor:pointer but no role=button, no tabIndex, and no key handler, making steps mouse-operable only and keyboard-unreachable/un-activatable.
- **Fix:** Make the clickable step node a real control only when interactive. Compute interactive props once inside the map: `const interactiveProps = clickable ? { role: 'button', tabIndex: 0, 'aria-label': step.title, onKeyDown: (e: React.KeyboardEvent) => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); onStepClick?.(i); } } } : {};` Spread `{...interactiveProps}` onto the same `<div onClick={handleClick} aria-current=...>` in both the horizontal (line 395) and vertical (line 448) branches, keeping the existing onClick. Add a visible focus outline (e.g. `outline` on `:focus-visible`) so keyboard focus is perceivable, and add a test asserting that Enter/Space on the focused step fires onStepClick and that the node exposes role=button + tabIndex=0 when clickable (and neither when not clickable).

### 9. TkxTabs
- **Violation:** WAI-ARIA APG Tabs roving keyboard navigation depends on an optional `tabCount` prop that defaults to 0 and is never derived from the actual tabs. With the default, Arrow/Home/End math targets non-existent tab ids and loses focus.
- **Fix:** Derive the count instead of trusting a hand-supplied prop. Best: have each TkxTab register/unregister its index in a context-held ref set and set tabCount = registeredIndices.size (robust to non-contiguous indices); keep the `tabCount` prop only as an optional override, defaulting to the derived value rather than 0. Simpler: count TkxTab elements in TkxTabs via Children.toArray(children). Minimal defensive guard in wcag.ts handleTabsKeyboard: early-return when tabCount<=0, and use modulo wrap so a bad count can never yield -1, e.g. next = (currentIndex + tabCount - 1) % tabCount for ArrowLeft/Up, (currentIndex + 1) % tabCount for ArrowRight/Down, and next = tabCount - 1 only when tabCount>0 for End. Ideally also skip `disabled` tabs when advancing.

### 10. TkxTabs
- **Violation:** Arrow-key navigation does not skip disabled tabs. handleTabsKeyboard (src/engine/wcag.ts:153-190) advances by raw index (next = currentIndex ± 1, lines 165/170) knowing only tabCount, with no disabled awareness. TkxTab's onKeyDown callback (TkxTabs.tsx:107-110) then unconditionally calls setActiveIndex(ni) — unlike onClick (line 106) which guards with !disabled. Result: pressing ArrowRight/Down onto a disabled tab marks it aria-selected=true and renders its panel (TkxTabPanel line 136), while document.getElementById(...).focus() (line 109) silently fails on the disabled button (disabled set line 90), leaving selection and keyboard focus out of sync.
- **Fix:** Give the keyboard handler disabled awareness and skip disabled tabs. (1) Track disabled indices in TabsContext: have each TkxTab register/unregister its index when disabled (e.g. a Set<number> plus register callbacks in the context value, or accept a disabledIndices prop on TkxTabs). (2) Extend handleTabsKeyboard with an optional isDisabled?: (index: number) => boolean param and, after computing next, loop forward/backward (wrapping via modulo over tabCount) until it lands on an enabled index; bail out if all are disabled to avoid an infinite loop. (3) In TkxTab's onKeyDown, pass that predicate and additionally guard the onSelect callback with a disabled check for defense in depth. Add a keyboard test asserting ArrowRight from an enabled tab adjacent to a disabled one lands on the next enabled tab and moves focus there.

### 11. TkxSpeedDial
- **Violation:** close() (lines 135-138) resets isOpen=false / focusedIndex=-1 but never returns focus to the main FAB. When the dial closes while focus is on an action button (rendered only under `isOpen`, line 250), that button unmounts and focus falls to document.body, violating the APG menu button pattern and WCAG 2.4.3 (Focus Order).
- **Fix:** Add a ref to the main FAB and restore focus when closing from the keyboard. e.g. `const mainButtonRef = useRef<HTMLButtonElement>(null);` attach it to the FAB button (line 332), and in close() refocus it: change close() to accept a flag / or unconditionally guard on prior focus: `const close = useCallback(() => { const hadFocus = containerRef.current?.contains(document.activeElement); setIsOpen(false); setFocusedIndex(-1); if (hadFocus) mainButtonRef.current?.focus(); }, []);`. Guarding on containerRef.contains(document.activeElement) ensures outside-click/backdrop closes (lines 145-149, 228) do NOT steal focus, while Escape/Enter paths correctly return focus to the FAB. Add a regression test asserting document.activeElement is the FAB after Escape.

### 12. TkxPopover trigger wrapper
- **Violation:** Trigger is a bare <div> carrying onClick, onKeyDown (Enter/Space), aria-expanded, aria-haspopup="dialog" and aria-controls but no role and no tabIndex, so it is not focusable and the popup-state ARIA lives on a generic, non-focusable element instead of a real control.
- **Fix:** Do not put interactive semantics on a generic div. Instead render the trigger as (or attach the behavior to) a real button. Preferred: replace the wrapper <div> with <button type="button"> that carries ref, onClick={toggle}, aria-expanded, aria-haspopup="dialog", aria-controls, and unstyled/inline-flex classes, e.g. <button ref={triggerRef} type="button" className={tkx('inline-flex')} onClick={toggle} aria-expanded={open} aria-haspopup="dialog" aria-controls={open ? popoverId : undefined}>{trigger}</button>. A native <button> is focusable and handles Enter/Space automatically, removing the need for the manual onKeyDown. If callers must supply their own interactive element, use React.cloneElement to merge ref, onClick, aria-expanded/aria-haspopup/aria-controls onto the child so the ARIA state lands on the focused control instead of a wrapper, and avoid nesting a button inside a button. Add tests asserting the trigger is focusable (tab order) and that the focused element exposes aria-expanded/aria-haspopup.

### 13. TkxSpeedDial
- **Violation:** The main FAB advertises aria-haspopup="true" (menu) and aria-controls={menuId} (lines 334-337), but menuId (lines 375-381) is a role="menu" div with style={{display:'none'}} whose children are non-interactive role="menuitem" text divs. display:none removes that menu from the accessibility tree, so the promised popup menu never materializes. The actions the user actually operates are separate <button> elements (lines 288-325) rendered in a sibling branch with implicit role="button", no role="menuitem", no aria-owns, and no membership in the announced menu. The exposed (hidden menuitems) and interactive (visible buttons) structures are disjoint.
- **Fix:** Make the exposed and interactive structures the same. Delete the hidden display:none menu div (lines 375-381). Wrap the visible action buttons in a container element that has id={menuId} role="menu" aria-label="Speed dial actions", give each action <button> role="menuitem", and render that container whenever isOpen so aria-controls resolves to a real, in-tree menu of operable menuitems. Alternatively, drop the menu semantics entirely: remove aria-haspopup and aria-controls from the FAB and the hidden div, and expose the actions as a labeled group/toolbar of buttons (role="group"/"toolbar" + aria-expanded on the FAB). Either approach makes the announced role match the operable controls; the current hidden-menu shim should not remain.

### 14. TkxDatePicker
- **Violation:** Combobox/Date Picker Dialog wiring + calendar tab order: the trigger input declares aria-haspopup="dialog" and aria-expanded but omits aria-controls, and the popup role="dialog" has no id, so the trigger→dialog relationship is never programmatically established; additionally the ~42 day-cell buttons have no roving tabindex, so every cell (plus nav/preset/footer buttons) is a separate Tab stop.
- **Fix:** 1) Give the dialog a stable id (e.g. const dialogId = `${id}-dialog`), put id={dialogId} on the role="dialog" div (1131), and set aria-controls={open ? dialogId : undefined} on the input (near 1667). 2) Implement roving tabindex on the day grid: track a single "active" cell (focusedDate ?? selectedDate ?? today); render each day button with tabIndex={isActive ? 0 : -1} so exactly one cell is in the Tab sequence. 3) Make handleCalendarKeyDown move real focus — keep refs to the day buttons and call .focus() on the newly focused date after arrow-key navigation (and preventDefault) so one Tab enters the grid and arrows navigate cells per APG. Optionally add role="grid"/role="row"/role="gridcell" wrappers. This confines the calendar to one Tab stop and exposes the trigger→dialog relationship without changing selection behavior or existing tests beyond the new tabIndex/focus expectations.

### 15. TkxDatePicker
- **Violation:** Date Picker Dialog / grid keyboard navigation: arrow-key handling never moves DOM focus and is unreachable from the input. handleCalendarKeyDown is bound to the portaled popup div[role="dialog"] (line 1134), but the input's onFocus only calls setOpen(true) (lines 1671-1679) and the input has no onKeyDown, so arrow keys pressed right after opening never reach the handler (the popup is portaled to document.body, line 1763, outside the input's bubble path). Even once a day button is focused via Tab, the handler only mutates focusedDate state (setFocusedDate, lines 1032-1051) without calling element.focus() or setting aria-activedescendant; day buttons have no roving tabIndex (lines 630-664). The colored 'focused' border moves while real DOM focus stays put, decoupling screen-reader announcement and Enter selection from the visible highlight.
- **Fix:** Adopt one coherent focus model per APG. Roving-tabindex approach: keep a ref map of day buttons keyed by cell index/date; render tabIndex={0} only on the cell matching focusedDate (falling back to selectedDate/today) and tabIndex={-1} on all others; in handleCalendarKeyDown, after computing next, call the target button's .focus() in a post-render layout effect so DOM focus tracks the highlight; and on open (input onFocus/toggle), move focus into the grid by focusing the selected/today cell so arrow keys work immediately. Add role="grid" to the day-grid container (line 571) and role="gridcell" semantics to cells. Alternatively use the aria-activedescendant model: make the dialog/grid focusable, focus it on open, set aria-activedescendant to the focused cell's id, and keep the key handler on that focused container. Also add a test that fires arrow keys starting from input focus and asserts document.activeElement moves, since the current tests dispatch keydown directly on the dialog and mask the defect.

### 16. TkxDrawer
- **Violation:** The role="dialog" aria-modal="true" panel sets aria-labelledby={title ? titleId : undefined} (line 170) with no aria-label fallback. When the optional `title` prop is omitted, the modal dialog is rendered with neither aria-labelledby nor aria-label, so it has no accessible name (WCAG 4.1.2 Name/Role/Value, Level A; ARIA APG dialog pattern).
- **Fix:** Guarantee an accessible name in every configuration. (1) Add an optional `ariaLabel?: string` prop to TkxDrawerProps. (2) On the dialog element, compute the name so it is never absent, e.g. give the element both: aria-labelledby={title != null ? titleId : undefined} and aria-label={title != null ? undefined : (ariaLabel ?? (3) Change the label condition to use title != null (or title !== undefined) to match the header's own rendering condition (line 187) so a falsy-but-present title still gets aria-labelledby. (4) Add a test asserting screen.getByRole('dialog') has an accessible name in the titleless case.

### 17. TkxColorPicker
- **Violation:** Popover rendered with role="dialog" (line 538) performs no focus management: openPicker() (lines 356-365) only calls setIsOpen(true) with no focus moved into the dialog; there is no focus trap; and neither the Escape handler (line 385) nor the outside-click handler (lines 370-377) returns focus to the trigger on close.
- **Fix:** Add focus management to the dialog: (1) give the popover div tabIndex={-1} and, in a useEffect keyed on isOpen, when it turns true call popoverRef.current?.focus() (or focus the first interactive control, e.g. the hex input); (2) trap Tab/Shift+Tab within the popover by querying its focusable descendants and wrapping focus at the ends; (3) on every close path (Escape handler at 385 and outside-click handler), call triggerRef.current?.focus() to restore focus to the trigger. Optionally guard the return-focus so it only fires when the active element was inside the popover.

### 18. TkxColorPicker
- **Violation:** The saturation/brightness area, hue track, and alpha track are plain <div>s driven only by onMouseDown + document mousemove/mouseup. They have no role="slider", no tabIndex, no keyboard (onKeyDown) handlers, and no aria-valuemin/max/now/valuetext, so they are operable only by mouse and cannot be focused or adjusted with the keyboard or announced to a screen reader.
- **Fix:** Promote each visual control to a real ARIA slider. For HueSlider and AlphaSlider: add role="slider", tabIndex={disabled?-1:0}, aria-valuemin/aria-valuemax/aria-valuenow (hue 0-360; alpha 0-100), aria-label ("Hue"/"Alpha"), and an onKeyDown handler where ArrowLeft/ArrowRight (and Up/Down) step by 1, Shift+Arrow or PageUp/PageDown step by ~10, and Home/End jump to min/max, each calling the existing onChange. For SatBrightPicker use role="slider" with aria-valuetext (e.g. `S ${sat}% B ${bright}%`) or better a 2D pattern: make the area focusable and handle all four arrow keys — Left/Right adjust saturation, Up/Down adjust brightness — via onChange(s,b). Also add a visible focus ring on each control. This keeps existing mouse behavior while making the visual pickers keyboard- and screen-reader-operable per the APG Slider pattern.

### 19. TkxRating
