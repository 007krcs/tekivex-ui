<Aside type="caution" title="What blueprints are and aren't">
  Industry blueprints show how tekivex-ui primitives help an application
  address specific technical requirements in regulated verticals. They do
  NOT make your application compliant with any framework — HIPAA, PCI-DSS,
  SOC 2, FedRAMP, or any other. Compliance attaches to **organizations
  and their processes**, not to npm packages. Each blueprint includes a
  large "what this does NOT cover" section naming the responsibilities
  your organization still owns. Read those sections.
</Aside>

## How to read a blueprint

Each page follows the same structure:

1. **The scenario** — what real-world workflow this addresses
2. **Framework mapping** — which specific regulatory subparts the primitives help satisfy (with citations)
3. **The blueprint** — full working code, typically multiple steps
4. **What's built-in** — the wins
5. **What this does NOT cover** — the larger compliance perimeter your organization still owns. Always large. Always specific.
6. **Gotchas** — real edge cases from the implementation
7. **References** — the actual statutes / regulations / standards cited

## Difference from recipes

[Recipes](/recipes/) are primitive-shaped — one focused pattern using one
to three library APIs. Industry blueprints are larger and compose more
primitives, with explicit framework citations. If you're trying to ship
*a feature*, look at a recipe. If you're trying to ship *a production
shape for a regulated industry*, look at a blueprint.
